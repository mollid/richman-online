# 大富翁 Online · 相机系统规格（hud-ac 原型）

对象：`design/hud-ac/`（three.js 2.5D 舞台 + PixiJS 叠加 + DOM 面板）。
落点：`world.js`（状态机与补间）、`hud.js`（调度与输入闸门）、`hud.css`（锁定态视觉）。
前置文档：`design/hud-ac/README.md`、`大富翁Online-HUD精细化规格.md`。
截图：`design/hud-ac/preview/cam-1..5-*.png`。

## 一、需求拆解与实现对应

| # | 需求原文 | 实现 | 落点 |
| --- | --- | --- | --- |
| 1 | 轮到某位玩家操作时，相机先**平滑拉近并聚焦**到该玩家 | `focusPlayer(pid)` → 注视点 + 俯角 + 距离三者同时补间，`easeInOutCubic`，1150ms | `world.js` |
| 2 | 随后进入**镜头跟随**状态，始终跟随当前正在操作的玩家 | 补间跑完自动转 `follow`；每帧 `k = 1 - 0.5^(dt/0.16)` 指数平滑追注视点 | `world.js` |
| 3 | 相机的移动与视角切换需保持**顺滑过渡** | 三次缓动 + 指数平滑；单帧最大位移 0.686 单位 / 相邻步长最大变化 0.0386（60fps 定步长实测） | `world.js` |
| 4 | **视角移动完全结束后**才允许该玩家进行操作 | 补间 `k >= 1` 的那一帧才 `setLocked(false)`；此时才发 `onCameraSettled` | `world.js` |
| 5 | 在此期间需**暂时屏蔽玩家输入** | 双路闸门：舞台事件 `if (locked) return`；HUD 侧 `.hud-shell--locked` + 捕获阶段点击拦截 | `world.js` / `hud.js` / `hud.css` |

## 二、状态机

```
        focusPlayer(pid)                     补间 k>=1
idle ──────────────────────▶ intro ──────────────────────▶ follow
  ▲                            │                              │
  │                            │ locked = true                │ locked = false
  │  setView(preset)           │ 掐断拖拽、清悬浮              │ 每帧指数平滑追注视点
  └────────────────────────────┴──────────────────────────────┘
                          releaseFollow()
```

- `idle`：完全交给用户。预设视角、拖拽、`setView()` 都在这一态生效。
- `intro`：**唯一会屏蔽输入的态**。`locked = true` 期间，五类舞台事件全部早退，HUD 全部按钮 `disabled`。
- `follow`：`locked = false`，输入已恢复。此时拖拽/滚轮只改 `az / el / dist`（跟随逻辑不碰这三项），所以「转视角」与「跟随注视点」互不打架。

**`prefers-reduced-motion: reduce`**：`focusPlayer()` 直接落到 `follow`（`cam.el/dist` 一次到位、`target` 直接置位），**不发 `intro`、不锁**。这是刻意的 —— 无障碍偏好优先于演出。

## 三、参数

```js
const CAM = {
  focusEl: 43,          // 近景俯角（全局默认 46°）
  focusDist: 54,        // 近景距离（全局默认 70）
  followClamp: 8,       // 注视点离棋盘中心的最大半径
  introMs: 1150,        // 入场时长
  followHalfLife: 0.16, // 跟随平滑半衰期（秒）
};
```

| 参数 | 值的由来 |
| --- | --- |
| `introMs = 1150` | 低于 ~0.8s 会「跳」过去，人来不及建立方位感；高于 ~1.5s 会被玩家当成卡住。1.15s 落在「可感知但不等」的区间。 |
| `followHalfLife = 0.16` | 指数平滑的写法 `k = 1 - 0.5^(dt/halfLife)` 与帧率无关。0.16s 的语义是「半帧位移只需 0.16 秒」——棋子跳格（每格 0.16s）时镜头略微滞后于棋子，读完有「追上去」的手感而不是瞬移。 |
| `focusDist = 54` | 受「棋盘要装得下」约束。更近（<45）会让中央岛与四边格子同时出画。距离还与 `applyCam()` 的 `frameScale()` 相乘，窄画面自动退远。 |
| `focusEl = 43` | 比全局 46° 略低。低一点能看清单格立面和彩色台座（那正是上一轮修好的「持有者标色」），高一点则更像战术地图。 |
| `followClamp = 8` | 见下节。 |

### 3.1 为什么注视点要夹取（`followClamp`）

棋盘 34 单位见方（64 格 × 2.0 间距）。近景 `dist = 54` 时竖直视野约 **29 单位**。

四个角上的格子在距环心 **22.6 单位**处。若把注视点直接钉在角落棋子上：

- 屏幕中心 = 该棋子；
- 棋盘中心距屏幕中心 22.6 单位 > 视野半高 14.5 单位 → **棋盘中心出画**；
- 玩家会看到「一片草地 + 一个棋子」，完全失去方位感，也没法做下一步决策。

所以跟随的是「朝玩家方向偏移、但离环心不超过 8 的**点**」。代价是注视点与棋子始终有距离，实测：

| 棋子所在 | 棋子离环心 | 注视点（夹取后） | 注视点↔棋子 | 备注 |
| --- | --- | --- | --- | --- |
| 第 36 格（下边） | 17.9 | (3.58, 7.16) | 9.9 | 视野内棋盘占比大 |
| 第 48 格（左下角） | 22.6 | (−5.66, 5.66) | 14.6 | **实测最大值** |
| 第 54 格（左下角，阿蓝起点附近） | — | 夹取到 r=8 | — | 同上 |

**「现在轮到谁」不靠镜头居中表达**，靠另外两处更稳的信号：

1. 棋子脚下的**地面高亮环**（`RingGeometry(0.6, 0.9)`，玩家色，带 3.1rad/s 脉动）；
2. 名牌的**金底 + ▶ 前缀**（奶油底 → `#fff3d6` + `#e0a51f` 描边）。

三条指示（镜头 / 高亮环 / 金底）都取同一个 `followPid`，实测换人后必一致（见验证表 §6）。

### 3.2 两个 dt 是分开的

```js
const rawDt = (now - clock.last) / 1000;
const dt     = Math.min(0.05, rawDt);   // 装饰动画：棋子呼吸、骰子旋转
...
stepCamera(Math.min(0.25, rawDt), t);   // 相机演出
```

- 装饰动画用 50ms 上限：卡顿后不要瞬间转半圈。
- 相机演出用 250ms 上限：它是**定时演出**，「1.15 秒后放开操作」这句承诺必须按墙钟兑现。

第一版两者共用 50ms 上限，结果在软件渲染（~11fps、帧间隔 ~110ms）下 1.15s 被拉成 **2137ms** —— 因为每帧只推进 50ms。这是量出来的（见验证表 §3）。

## 四、输入闸门的双路设计（需求 5 的关键）

只在一个地方判断「锁没锁」一定会漏。实际用了两路：

### 路一：舞台（`world.js`）

```js
host.addEventListener('pointerdown', (e) => { if (locked) return; ... });
// pointermove / pointerup / wheel / keydown 同样处理
```

- `locked` 置起的**那一瞬间**主动掐断正在进行的拖拽并清悬浮（`drag = null; setHover(null)`），否则会出现「入场时手指还按着，视角跟着手指飘」。
- **`pointerleave` 不拦** —— 拦了鼠标移出时悬浮状态会卡死。

### 路二：HUD（`hud.js`）

```js
shell.addEventListener('click', (e) => {
  if (!HUD_LOCKED) return;
  const t = e.target.closest('button, [role="button"], a');
  if (t && t.hasAttribute('data-cam-demo')) return;   // 唯一放行
  e.preventDefault(); e.stopPropagation();
  if (t) toast('🎥 镜头正在聚焦，等视角停稳再操作', 'bell');
}, true);
```

三个设计点：

1. **捕获阶段**。若只在 `cosmetic()` 里判断，会漏掉三类旁路：页签切换、`[data-post]` 挂出、商店/卡片道具格。捕获阶段挂在整个 `shell` 上，一次覆盖全部。
2. 键盘回车走的是 `primary.click()`，是真实 click，因此同样被捕获 —— 不用额外写键盘分支。
3. **唯一放行的是「🎥 镜头巡演」按钮**。它是驱动镜头的入口，被自己锁死就没法验收了。

另外两处补强：

- `.hud-camtag--lock` 提示条（`[data-cam-lock]`）—— 让「为什么点不动」可见；
- 弹层在锁上瞬间自动收起（`.hud-pop--open` 移除）—— 否则弹层会浮在灰壳上，看着仍可点。

**诚实的边界**：这是原型级闸门，不是安全边界。控制台里 `D25World.focusPlayer` / `__camTour` 仍然可调 —— 它们本来就是给脚本验收用的。

## 五、入口与调度

| 入口 | 用途 |
| --- | --- |
| `D25World.focusPlayer(pid, opts)` | 唯一聚焦入口。`opts.immediate` 跳过补间；`opts.el / opts.dist` 覆盖近景参数 |
| `D25World.releaseFollow()` | 释放跟随、回自由视角。**`setView(preset)` 内部会先调它** —— 否则用户手选的机位下一帧就被跟随逻辑拽回玩家身上 |
| `D25World.isCameraLocked()` | 输入是否被屏蔽（供 HUD 与脚本读） |
| `D25World.cameraState()` | `{ state, pid, locked, tx, tz, prog }`。`prog` 是补间进度 0→1，把「演出时长是硬承诺」暴露出来，脚本才能断言而不是只看「感觉挺顺」 |
| `__camTour(step)` | 镜头巡演：按环序交给下一位玩家 |
| `__setTurn(i)` | 把回合指针挪到第 i 位，走「换人 → 自动聚焦」**真实路径**（仅脚本用，见下） |

HUD 侧的调度写在 `syncStage()` 里，顺序很关键：

```js
globalThis.D25World.sync(S);
globalThis.D25World.paintOwners();
// ① 先决定镜头目标
if (!camFocused) { /* 首屏：420ms 后 scheduleFocus(activePid) */ }
else {
  const turnPid = st.players[st.currentPlayerIndex].id;
  if (turnPid !== lastTurnPid) { lastTurnPid = turnPid; scheduleFocus(turnPid); }
}
// ② 再重建叠加层 —— 名牌金底取自「跟随中的人」，顺序反了金底会停在上一回合的玩家身上
globalThis.D25Overlay.rebuild();
globalThis.D25World.renderOnce();
```

两个反直觉点：

- **判据必须是「回合指针是否变化」（`lastTurnPid`），不能用 `activePid` 比对**。巡演会把 `activePid` 挪到别人身上，用 `activePid` 比对的话每次 `render()` 都会把镜头从巡演目标拽回快照里的当前玩家。
- **`scheduleFocus` 必须排在 `Overlay.rebuild()` 之前**。金底取 `tokenAnchors().cur`，而 `tokenAnchors().cur` 优先取 `followPid` —— 先 rebuild 再换目标，金底就停在上一回合的玩家身上。只差一帧，但那一帧之后没人再 rebuild，就一直是错的（实测抓到这个错位后调整顺序，见验证表 §6）。

### 5.1 为什么原型不给一个「换人」按钮来触发

需求场景是「轮到某位玩家」。理论上做一个一键换人的按钮最直观，但**做不了**
（而真游戏里也已经没有这颗按钮 —— R4 之后玩家手上不存在「结束回合」，回合是事件处理完自己走的，
唯一由玩家按的是落格窗那个「离开 / 不做」的情境出口）：

`snapshot.js` 是 `tools/dump-snapshot.mts` 跑真实引擎导出的一帧，其中 `view.actions`（动作位门控）、`view.assets`、`A.canRoll / canBuy / ...` 全部由引擎针对 `view.myPlayerId` 派生。原型里没有引擎，**重算不了**。若按钮只推进 `currentPlayerIndex`：

- 会出现「脚下格是甲的地，主按钮却是乙的门控」这种自相矛盾；
- 违背 README 第一条「这只是表现层，不跑规则」。

所以改为两个自检钩子，且**刻意不做成界面按钮**：

- `__camTour()` → 有一颗真实的「🎥 镜头巡演」按钮（只动镜头，相机条上写明「原型只动镜头 · 不改回合」）；
- `__setTurn(i)` → 只给脚本用，走「换人 → 自动聚焦」真实路径，用于验证需求 1。

## 七、本轮额外修掉的两个既有缺陷

都不是本轮需求，是量布局时撞出来的。

### 1. 1024×768 下 2.5D 棋盘只剩 6px 边框高

**现象**：`.hud-host` 与 `.d25-stage` 实测 6px，`canvas` **0px** —— 棋盘整块不可见。

**根因**：`@media (max-width: 1120px)` 改成单列堆叠后 `shell { height: auto }`，棋盘行高变成 `auto`。而
- `.d25-host { flex: 1; min-height: 0 }` → 弹性基准 0；
- `.d25-stage { height: 100% }` → 百分比高度对不定高父级无解，按 0 处理。

两者叠加，整块塌成 `.d25-legend` 那一行的高度（29.75px）。

**改法**：

```css
@media (max-width: 1120px) {
  .hud-board .d25-host { flex: none; }
  .hud-board .d25-stage { height: min(74vh, 88vw); }
}
```

复测 1024×768 → **568px**。修复前后对比见 `preview/cam-5-1024x768-fixed.png`。

### 2. 「镜头聚焦中」提示条在解锁后不消失

**现象**：DOM 属性 `[data-cam-lock].hidden === true` 但提示条仍然挂在界面上。

**根因**：`hidden` 属性的 `display: none` 来自 **UA 样式表**，而 `.hud-camtag { display: inline-flex }` 是**作者样式** —— 作者样式优先级更高，把 `hidden` 整个吃掉了。

**改法**：显式补一条

```css
.hud-shell [hidden] { display: none !important; }
```

**教训（已写进 CSS 注释）**：断言 `hidden` 这种 DOM 属性会漏掉这类缺陷 —— 它的值确实是 `true`。必须读 `getComputedStyle(el).display`。第一版脚本就是读 `.hidden` 才放过它的。

### 3. ≤960px 横向溢出 621px（390px 视口）

**现象**：390×844 下 `documentElement.scrollWidth` 比 `clientWidth` 大 **621px**。

**定位过程**（两次都找错了对象）：

1. 先扫「宽度 > 400px 的元素」，只命中 `.hud-cambar = 439px` → 结论「相机条撑破的」。
   → 加 `@media (max-width: 960px) { .hud-dock { grid-template-columns: minmax(0,1fr) } }`，**实测溢出仍是 621px**。
2. 复扫发现 `.hud-cambar` 回到 370px，且**没有任何元素宽于 395px**，但 `body.scrollWidth` 仍是 1011。
   → 改扫「右边缘越界的元素」，才拿到真凶。

**真因**（两处，与相机条无关）：

| # | 元素 | 原因 | 改法 |
| --- | --- | --- | --- |
| a | `.hud-dock` | `≤1120px` 已改单列堆叠，但 dock 仍用三列模板 `190px + 1fr + auto`；`auto` 那列被「更多动作 / 被挡住 n / 主按钮 / 结束回合」撑到 500px+。相机条 `grid-area` 横跨三列，把总宽原样继承，所以**看起来像相机条的问题** | ≤960px 时 dock 也改单列 |
| b | `.hud-top` + `.hud-status` | 两者都是 `flex-wrap: nowrap`，内部 chip 全是 `flex: none`。顶栏（三币 + 6 个跳转按钮）390px 下排到 **920px**；状态条 8 个指数 chip 自己就超一屏 | ≤960px 时允许换行，`.hud-status__sep` 隐藏，行情带独占一行 |

修后 390×844 横向溢出 = **0**。

**附带教训（写在 `hud.css` 末尾注释里）**：改这类媒体查询时踩了**源码顺序**的坑 —— 基础 `.hud-dock` 规则在同文件上方、与覆盖规则**特异性相同**（0,1,0），同特异性下由源码顺序决定胜负，所以写在文件上方的媒体查询会被基础规则反过来覆盖。第一次加 dock 单列规则时就是因此静默失效的（表现：改了等于没改，溢出数字一模一样）。凡「特异性打平 + 想覆盖」，位置必须在下。

## 八、没做 / 已知限制

1. **跟随 ≠ 贴身**。`followClamp = 8` 的夹取让注视点与棋子最多差 14.6 单位。要贴身得先做镜头分级（全局 / 半区 / 单格）或把棋盘改成滚动视口 —— 那是另一件事，本轮只交付「聚焦 → 跟随 → 锁 → 解锁」这条链。
2. **巡演不改回合**。dock 的「脚下格」在巡演期间仍是快照基准回合的那位。相机条上写明了原因。
3. **闸门是原型级**。控制台可绕过（本来就是留的验收钩子），不是权限边界。
4. **跟随期拖拽不脱离**。`follow` 只写 `target.x/z`，用户转方位角/俯角不会取消跟随。要自由看局得点「复位 / 正俯视 / 斜 45° / 低角度」。
5. **低帧率下演出会变阶梯**。250ms 的 dt 上限意味着低于 4fps 时时长会失真；同时低帧率下单帧步长可达 6~8 单位（这是帧率问题，不是缓动问题，见 §6.1）。
6. **`focusDist = 54` 是硬编码的近景距离**，尚未与棋盘缩放、单格尺寸联动。若后续换棋盘尺度或改 `SPACING`，需要同步重算 —— 建议改成由「棋盘包围盒 + 目标视野占比」反推。
7. **未做**：镜头碰撞（穿模到地形下方）、多棋子同框取景、聚焦时的其他棋子避让。

## 九、进引擎落地时的对应参数（如后续转 Cocos / Unity）

| 原型值 | 语义 | 建议落点 |
| --- | --- | --- |
| `introMs = 1150` | 聚焦演出时长 | 相机 Timed 组件时长；**用真实 deltaTime，不要 clamp 到 50ms** |
| `easeInOutCubic` | 缓动曲线 | EaseInOutCubic / ease-in-out-cubic |
| `followHalfLife = 0.16s` | 跟随平滑半衰期 | `k = 1 - pow(0.5, dt/halfLife)`，不要用固定 lerp 系数（会与帧率耦合） |
| `focusDist = 54 / focusEl = 43` | 近景距离 / 俯角 | 由棋盘包围盒反推，别硬编 |
| `followClamp = 8` | 注视点离环心最大半径 | 建议改为「视口内至少保留 N% 棋盘」的可视性约束 |
| `RingGeometry(0.6, 0.9)` + 3.1rad/s 脉动 | 当前玩家地面高亮环 | 独立的 highlight decal，勿用后处理描边（成本高且与地形 Z 冲突） |
| `camTween` / `camState` | 状态机 | 相机控制器三态枚举；`locked` 作为对外只读属性 |
| `onCameraLock` / `onCameraSettled` | 输入闸门开关 | 输入系统订阅该事件做 `inputEnabled` 切换；**不要**在每个 UI 按钮里各判一次 |
